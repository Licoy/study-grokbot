## What this issue covers {#intro}

The first four issues covered splitting up work, schedules, skills, and the cloud computer. The more a Bot can do, the more one question matters: what can it do by itself, and what must it ask you about first?

Grok Bot handles this in two layers. The first is the boundary you write into your request. The second is Auto-review, which checks each action before the Bot takes it and shows an approval card when you need to decide. This issue explains both layers and shows how to write a few Custom Rules that actually help.

::: callout The one thing to remember
Put the boundary in the request. Read the target before you press a button on a card. One rule per action, narrow beats broad. Auto-review adds safety; it isn't all of it.
:::

## Five tips you can use today {#tips}

Each tip comes with an example prompt. Replace the parts in brackets with your own and send it to your Bot.

### Tip 1: Write the boundary into the request {#tip1}

The official docs put it plainly: the strongest boundary is the one in the request itself. Tell the Bot which actions it can take and where it must stop. The docs' example: reconcile the campaign data and draft a recommended budget change; don't change the campaign or message the agency; ask for approval after showing the current value, proposed value, and expected impact.

The docs recommend explicit boundaries for:

::: props
- Sending: Messages or invitations
- Publishing: Content that goes public
- Money: Purchases and financial transfers
- Deleting: Deleting or overwriting data
- Permissions: Changing who has access
- Production: Changes to live systems
- Legal terms: Accepting any agreement
:::

One more thing: an approval controls the proposed action. It doesn't reverse work already completed. So state boundaries before the work starts, not after.

::: prompt
Please handle [task]. Boundaries:
1. You may read [data source], put it in a table, and draft a recommendation;
2. Don't send any messages and don't change any settings in [system name];
3. Before making a change, show me the current value, proposed value, and expected impact, and wait for my approval.
:::

### Tip 2: Know every button on an approval card {#tip2}

When Auto-review decides an action needs your OK, the Bot shows a card in your chat with the proposed operation and its inputs. The three main buttons:

::: props
- Allow once: The Bot does the action now. No rule is saved
- Always allow: The Bot does the action now and saves an Allow rule to your Custom Rules, so similar actions run on their own
- Deny: The Bot doesn't do it, and won't try that action again or ask you about it until you send another message
:::

Some cards use other labels. A terminal command card shows Allow and Skip, plus Manage settings. A card paused by one of your Ask first rules shows Allow and Not now. When there's no rule to offer, you see Allow and no Always allow. Some cards also carry a warning, such as This can't be undone, This changes sign-in or security settings, or This shares your data outside this chat.

The docs are firm on this: don't approve an action whose target or effect you can't identify. Ask the Bot to explain it in plain language, or to produce a draft first.

::: prompt
I don't understand the approval card you just showed. Don't run it yet. In three sentences, tell me:
1. Exactly what this action changes, and on which account or file;
2. Whether it can be undone, and how;
3. Whether there's a safer option, such as a draft or a read-only preview.
:::

### Tip 3: Keep Custom Rules narrow, one action each {#tip3}

With Auto-review on, Custom Rules appears under the switch in Settings → General, in the Bot section. Adding a rule takes three steps:

::: steps
- Describe the action | Under When Grok Bot wants to:, describe one action in plain words, like "reply to emails for me."
- Pick the behavior | Under It should:, choose Allow automatically or Ask first.
- Add it | Press Add Rule.
:::

The hard rules about rules:

::: props
- Ask first: Matching actions always stop for you
- Allow automatically: Matching actions proceed only when the review finds no other reason to stop
- Conflicts: If both kinds match, Ask first wins
- Limits: Up to 20 of each kind, up to 1,000 characters each. At 20 Allow rules, Always allow on a card removes your oldest Allow rule and tells you which one
- Every device: Personal rules are saved to your account, so they apply on desktop and mobile
:::

::: proscons
#### Good rules
- Ask first before sending any external email
- Ask first before changing a production dashboard
- Allow automatically when checking repository status read-only in one reports folder

#### Bad rules
- Allow everything in the browser
- Allow every command
- One rule that bundles several unrelated actions
:::

Websites and tool behavior change over time. A broad Allow rule that's safe today may not be safe next month.

::: prompt
Based on how we've worked together this past month, please draft a list of Auto-review Custom Rules:
1. Actions that should always be Ask first (for example external sends, deletions, payments);
2. Read-only, low-risk, recurring actions that could be Allow automatically, each with a clear action and scope;
3. Keep each rule to one sentence.
Just give me the list. I'll add them in Settings myself.
:::

### Tip 4: Background cards expire, so plan for it {#tip4}

What happens when nobody answers a card depends on how the work started:

::: props
- Started from a chat message: The card waits for an answer and doesn't expire on a timer
- Raised by a routine, an incoming message, or other background work: It expires after 30 minutes
- You send a new message: Any open card in that chat closes
- You change Auto-review settings: Open cards close too
:::

A closed card shows Expired and says the Bot didn't take the action. If the card offered a rule, you can still press Always allow next time. To finish the task now, ask the Bot to try again.

Email from the Bot's own address has its own rules. Email you ask for in chat goes out once Auto-review allows it. Email from a routine, an incoming message, or other work you didn't start with that request waits as a draft until you press Send. A forward, or an email with an attachment Auto-review can't fully read, always waits for your OK.

So when you design a routine, don't count on it waiting overnight for your approval. A steadier pattern: the background work prepares and drafts, and the decisions wait for when you're awake.

::: prompt
Please review my current routines:
1. Which steps might raise an approval card (sending, deleting, changing settings, and so on)?
2. Could those steps become "draft only, and remind me to confirm in the morning summary"?
3. List the suggested changes. Don't change any routine yet.
:::

### Tip 5: Control execution on your local computer {#tip5}

Bots normally work on the cloud computer. The computer in front of you is separate: whether a Bot may run commands on it is its own setting, under Settings → Computer → Your computer, with Ask every time, Always allow, or Never allow.

::: props
- Default: Ask every time
- The docs' advice: Use Never allow unless a Bot has a specific reason to work on your local files
- Team cap: Your admin can cap this for the whole team; when the team's policy is stricter, it applies
- Independent: This setting doesn't stop the Bot from using its cloud computer
:::

The first time a Bot asks to run a command on your computer, the chat asks whether to allow Grok Bot and all Bots to run commands on your local computer. Note that choosing Always allow or Never there applies to every Bot. You can change it later in Settings.

::: prompt
The next piece of work should only use your own cloud computer. Please confirm:
1. This task doesn't need to run any command on my local computer;
2. If you find midway that it really does, stop and tell me which command and why, and wait for my decision.
:::

## Limits you should know {#limits}

::: steps
- Outside text isn't your request | Auto-review counts what you ask for in your own messages. Instructions in an email or on a web page don't count.
- Not every side effect is reviewed | Memory writes and most settings changes aren't covered. Back safety boundaries with approval rules and least privilege, not a line in memory alone.
- Built-in checks always apply | Whatever your Custom Rules say, the built-in safety checks still run.
- In group chats, only the asker approves | Only the person whose message the Bot is answering can approve; others see who the card is waiting on. Group chat cards don't offer Always allow.
- Team rules only get stricter | When your admin enforces Auto-review, you can't turn it off. Your own rules sit on top of the team's and can only make behavior stricter.
:::

## Case study: putting brakes on a newsletter team {#case}

Continuing the fictional lineup from earlier issues (not anyone's real setup): a small team publishes a weekly newsletter and maintains a side-project app. This time they listed, for each Bot, what it can do alone and what it must ask about:

| Bot | Can do directly | Must ask first | Rule idea |
| --- | --- | --- | --- |
| Research Bot | Search, read, take notes | Paid subscriptions | Ask first before any payment |
| Writer Bot | Draft and revise | Publishing to public channels | Ask first before publishing anything |
| Reviewer Bot | Check sources, flag issues | Nothing | Read-only work, no extra rule needed |
| Planner Bot | Read calendars, propose schedules | Sending invitations to others | Ask first before sending invitations |
| Builder Bot | Run tests in the workspace | Deploying to production, deleting branches | Ask first before production changes |

### Highlight: draft overnight, decide in the morning {#case-flow}

Writer Bot has a routine that runs early each morning to prepare the day's newsletter. Because background cards expire after 30 minutes, they didn't let it publish directly. It only drafts, and the morning summary reminds you to confirm.

::: flow
- Writer Bot | Drafts the issue early in the morning
- Reviewer Bot | Checks sources and flags issues
- Me | Reads the summary and confirms | person
- Publishing channel | Goes public
---
- Writer Bot → Reviewer Bot: hands over the draft
- Reviewer Bot → Me: attaches the review
- Me → Publishing channel: publishes after approval
- Publishing channel ⇢ Me: alerts me if something is blocked
:::

No unanswered card quietly expires overnight, and in the morning you make just one decision.

::: prompt
You're this team's Planner Bot. For Research Bot, Writer Bot, Reviewer Bot, and Builder Bot, list what each can do directly and what it must ask about first,
and write a one-sentence Ask first rule for each action that must be asked about. Plan only; don't change any settings.
:::

## Community picks: common ways to use approvals {#community}

Here are a few common, easy-to-start ideas. They're general, so swap in your own details.

### Draft first, send later {#c1}

Have the Bot draft every outgoing message, email, and post for you to read. A draft carries no risk; approve the send once it looks right.

### The before-and-after trio {#c2}

Ask the Bot to show the current value, proposed value, and expected impact before any change. Approvals become a glance, and you get a record for later.

### Prune Always allow regularly {#c3}

Press Always allow often enough and your rule list gets broad. Every so often, open Custom Rules and delete Allow rules you no longer need or that have grown too wide.

### Read-only first {#c4}

When you connect a new tool, start the Bot on read-only tasks, then open up writes step by step once they run smoothly. It's the first step in the docs' least-privilege advice.

### When in doubt, ask it to explain {#c5}

If a card doesn't make sense, don't press anything. Ask the Bot what the action changes and whether it can be undone, then decide.
