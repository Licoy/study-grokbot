## What this issue covers {#intro}

Issue 1 covered creating and managing multiple Bots. This issue goes deeper on collaboration: when to open a group, how to assign owners at kickoff, how async handoffs work, how attachments travel, and the shared-computer and group-memory boundaries.

Grok Bot can work alone or with other Bots. Groups fit shared outcomes with visible handoffs. Bot-to-Bot handoffs fit "A owns the source, B owns the deliverable." Pick the right shape and the work stays clear; pick the wrong one and you get duplicate effort and noisy updates.

::: callout The one thing to remember
Open a group for a shared outcome; one owner per stage; handoffs are async and visible; send images to the Bot that must see them; treat the shared computer and group speech as open boundaries.
:::

## Five tips you can use today {#tips}

Each tip comes with an example prompt. Replace the parts in brackets with your own and send it to your Bot.

### Tip 1: Tell a group chat from a Bot handoff {#tip1}

The official docs draw a clear line between the two collaboration shapes.

Open a group when:

::: props
- Shared outcome: Several Bots need to finish one result together
- Visible handoffs: You want to see who took what and what they passed on
- Size: New chat with two to six Bots
:::

Prefer an async Bot-to-Bot handoff when:

::: props
- Source vs deliverable: One Bot owns a source system; another owns the final output
- Long-running work: The job should continue without you coordinating every step
- Still visible: You can see the handoff in the conversation
:::

Your Primary Bot is the main point of contact: it checks in on its own and can pass work to a more specialized Bot. A Shared Bot can't be primary. Day to day, you can send work to Primary and let it hand off by role.

::: prompt Example prompt · copy and send to your Bot
Help me decide whether this task should be a group chat or an async Bot-to-Bot handoff:
Goal: [one-sentence outcome]
Roles involved: [2–6 role names]
Do I need to see every handoff: [yes/no]
Who owns the source system: [Bot name]
Who owns the final deliverable: [Bot name]
Give a three-sentence recommendation with reasons. Don't create a group or start a handoff yet.
:::

### Tip 2: Assign one owner per stage at kickoff {#tip2}

After you open the group, describe the outcome and @mention one owner for each stage. Write normally so Bots decide who replies; type @ to hand work to one teammate; save @everyone for group-wide updates.

The docs' kickoff example is plain:

::: prompt Example prompt · copy and send to your Bot
@Researcher gather the source material and link every claim. @Writer turn the findings into a launch draft. @Reviewer check the draft against the sources and list only blocking issues. Don't publish anything.
:::

"One Bot responsible for each step" is the habit that keeps collaboration clean. Spell it out at kickoff so teammates don't race the same stage or drop it.

::: prompt Example prompt · copy and send to your Bot
We're opening a group to deliver: [final outcome].
Participants: @Researcher @Writer @Reviewer @Planner
Claim one owner per stage (only one person each):
1. Gather and verify sources;
2. Turn findings into a draft;
3. Check the draft against sources and list only blockers;
4. Summarize progress back to me.
Confirm the kickoff, then start stage 1. Don't send or publish anything externally until I explicitly approve.
:::

### Tip 3: How handoffs work—and the Slack rules {#tip3}

A Bot can send an asynchronous message to another Bot. That Bot wakes, handles the request, and can reply later; you see the handoff in the conversation. It fits when one Bot owns a source system and another owns the deliverable, or when a long-running job should continue without you coordinating every step.

The hard constraints:

::: props
- One owner per stage: Parallel handoffs for the same stage create duplicate work and noisy updates
- App or your own Slack DM: Any Bot can hand off work
- Slack channel thread: Only a shared Bot can, on behalf of the person who mentioned it
- Acting for one person: A handoff needs a Bot acting for one person
:::

Your DM takes priority over background work. Say "Stop now" to end work immediately—it stops current work but does not undo completed actions.

::: prompt Example prompt · copy and send to your Bot
Please run one handoff under these rules (say who you'll pass to and what you'll pass, then do it):
1. Current-stage owner: [current Bot];
2. Next-stage owner: [next Bot];
3. Handoff payload: [material summary / todo list / blockers];
4. Do not fan out this stage to any other Bot in parallel.
After the handoff, confirm in this chat with one sentence. Don't publish or send externally without approval.
:::

### Tip 4: You can attach in a group; Bot→group is text-only {#tip4}

Your messages in a group can include attachments. Bot-to-group handoff messages are text-only—when a teammate must inspect an image, send that image directly to the Bot instead of expecting a group handoff to carry it.

A practical split:

::: props
- You → group: Screenshots, sheets, and documents are fine
- Bot → group: Text-only summary and links
- Bot → specific Bot: Send the image directly when that Bot must see it
:::

When you write a handoff summary, spell out conclusions, links, and blockers; keep anything that must be "seen" for a direct send.

::: prompt Example prompt · copy and send to your Bot
Prepare a group handoff summary (text only—do not try to embed images in the group handoff):
1. What this stage finished;
2. Key links and sources;
3. Next-stage owner and todos;
4. Blocking issues (if any).
If any screenshot must be inspected by the next owner, list those files first and wait for my OK before sending them directly to that Bot.
:::

### Tip 5: Shared computer and group-memory boundaries {#tip5}

All your Bots share one computer: files and browser sessions are shared. Each Bot gets its own screen (one computer-use task per screen at a time), but screens are not security boundaries. Don't put a credential on that computer if another of your Bots shouldn't use it.

Group memory rules matter just as much:

::: steps
- Private context can be used | In a group chat, your Bot can use what you told it in private.
- Memory isn't shared between Bots | Each Bot keeps its own memory and doesn't share it with the other Bots there.
- Spoken words are visible | Everyone in the group can read what your Bot says.
- Say what must stay out | Tell it explicitly if something should stay out of the group.
:::

You can also @mention a Bot, a group, a routine, or an app to point attention at that target.

::: prompt Example prompt · copy and send to your Bot
Please confirm and follow these collaboration boundaries:
1. Do not store [sensitive credential class] on the shared computer;
2. In group chats, share only public-safe summaries; never repeat: [forbidden items];
3. When another Bot must see an image, send it directly—don't try to carry it in a text-only group handoff;
4. Keep a single owner per stage; no parallel fan-out of the same task.
Restate in four sentences how you will comply.
:::

## Limits you should know {#limits}

::: steps
- Group size | New chat with two to six Bots—not an unlimited room.
- Use @everyone sparingly | Save it for group-wide updates; day-to-day work goes to a named owner.
- Parallel handoffs get noisy | One owner per stage avoids duplicate work and noisy updates.
- Slack channel limit | In a channel thread, only a shared Bot can hand off on behalf of the person who mentioned it.
- Bot→group is text-only | When a Bot must see an image, send it directly to that Bot.
- Screens aren't isolation | A credential on the shared computer may be usable by your other Bots.
- "Stop now" doesn't undo | It ends current work immediately but does not reverse completed actions.
:::

## Case study: a joint issue for the newsletter team {#case}

Continuing the fictional lineup from earlier issues (not anyone's real setup): Research Bot, Writer Bot, Reviewer Bot, Planner Bot, and Builder Bot. This time they need one shared launch note with visible handoffs, so they open a group instead of bouncing private DMs.

| Stage | Sole owner | Input | Output | Don't |
| --- | --- | --- | --- | --- |
| Gather | Research Bot | Topic and scope | Source pack with links | No drafting, no publishing |
| Draft | Writer Bot | Source pack | Launch draft | Don't change source conclusions |
| Review | Reviewer Bot | Draft + sources | Blocking-issues list only | Don't silently rewrite or publish |
| Coordinate | Planner Bot | Stage returns | Progress and next step | Don't fan the same stage to many Bots |
| Layout (optional) | Builder Bot | Final structure | Page/template checklist | No credentials, no auto-ship |

### Highlight: kickoff claims → async handoffs → text-only in the group {#case-flow}

They kept one outcome, one main line, and one owner per stage. When a screenshot had to be inspected, the current owner sent it directly to the next Bot.

::: flow
- Me | Opens the group and @mentions one owner per stage | person
- Research Bot | Gathers material and links every claim
- Writer Bot | Turns findings into a launch draft
- Reviewer Bot | Checks against sources; lists only blockers
- Planner Bot | Summarizes progress and asks whether to continue
---
- Me → Group: kickoff claims and "Don't publish anything"
- Research Bot → Writer Bot: source-pack handoff (text summary in group)
- Writer Bot → Reviewer Bot: draft handoff
- Reviewer Bot → Planner Bot: blocker list
- Planner Bot → Me: asks whether to continue
:::

If a figure must be "seen" by Reviewer Bot, Writer Bot sends the image directly and leaves only a text note in the group. Primary (if Planner Bot is also the main contact) follows up on blockers instead of letting everyone race the same stage.

::: prompt Example prompt · copy and send to your Bot
You're this team's Planner Bot. Draft a group kickoff for one newsletter issue:
1. One-sentence final outcome;
2. @mention sole owners for gather / draft / review / coordinate;
3. Include "Don't publish anything";
4. Remind everyone: group handoffs are text-only; send images directly when a Bot must inspect them.
Kickoff copy only—don't start the work.
:::

## Community picks: common ways to collaborate {#community}

Here are a few common, easy-to-start ideas. They're general, so swap in your own details.

### Smallest useful group {#c1}

Research, Writer, and Reviewer only. Three @claims at kickoff beat five Bots entering at once.

### Keep a kickoff snippet {#c2}

Store "outcome + one owner per stage + don't publish" as a reusable snippet. New projects only swap role names.

### Route blockers through Planner {#c3}

Questions go to @Planner first so the same question isn't answered by several Bots at once.

### Split attachments by direction {#c4}

You drop large attachments into the group; Bots pass summaries and links to each other; image-must-see steps go point to point.

### Seal private context before the group {#c5}

Before kickoff, tell each Bot which private-chat details must never be repeated in the group; leave only public-safe summaries there.
