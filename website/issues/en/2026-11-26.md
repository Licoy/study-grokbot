## What this issue covers {#intro}

After a while with GrokBot, many people notice that the same Bot sometimes gets it right the first time and sometimes takes a long detour and needs rework. The difference is often not the Bot but how clearly the work was handed off.

The official docs have a short section on keeping conversations effective, and related advice is spread over a few other pages: how to write a first task, how to set boundaries in a request, how to change course mid-task, and how to use threads and search. This issue pulls them together into five habits you can start using now. For errands like draft review and phone calls, see [Issue 23](/issues/2026-11-23/). For the full list of shortcuts, see [Issue 17](/issues/2026-11-17/).

::: callout The one thing to remember
Say what result you want, then how far the Bot may go. Ask for evidence, say so when you change your mind, and use search to bring back past work.
:::

In the docs' words, GrokBot is designed to feel like messaging a teammate. Keep requests natural, but make the outcome and the decision boundary explicit: what the Bot may change, and where it must stop for you.

## Five tips you can use today {#tips}

Each tip comes with an example prompt. Replace the text in square brackets with your own and send it.

### Tip 1: Ask the way you'd ask a coworker {#tip1}

The official getting-started guide says to ask the way you'd ask a coworker, and to cover four things.

::: steps
- What you want back | A summary, a draft, or a table at the end.
- Which sources | Your inbox, calendar, or a specific doc. Linking the source of truth is best.
- Any limits | Scope, time range, format, and what not to do.
- When to check with you | Which situations should make it stop and ask.
:::

The docs also advise leading with the result you need rather than a detailed imitation of every click. Leave the steps to the Bot, and keep your part to the goal and the boundaries.

Besides typing, you can paste links and images, attach local files, dictate, ask for a saved skill by name, or use `@` to mention a Bot, group, routine, or app.

::: prompt
Please [the result, for example: pull out the top five issues from this week's customer feedback].
Use only [source link or app name], covering [time range].
Return it as [format, for example: a five-row table with the original link on each row].
If the sources are missing data or contradict each other, stop and ask me first.
:::

### Tip 2: Set boundaries in the request {#tip2}

Approval cards stop sensitive actions before they happen, but it's safer to write the boundary into the request itself. The docs recommend explicit boundaries for these:

::: props
- Outreach: Sending messages or invitations
- Publishing: Publishing content
- Money: Purchases and financial transfers
- Data: Deleting or overwriting data
- Access: Changing permissions
- Live systems: Production changes
- Legal: Accepting legal terms
:::

The official example states the work first, then what not to do, then when and with what details to ask for approval. Keep in mind that an approval controls the proposed action and doesn't reverse work already completed.

::: prompt
Reconcile [the data, for example: last month's ad campaign data] and draft a recommended budget change.
Don't change any campaign settings, and don't message anyone.
When you need my approval, show the current value, the proposed value, and the expected impact, then wait for my reply.
:::

### Tip 3: Ask your Bot for evidence {#tip3}

The docs suggest asking for evidence: links, screenshots, or a short action log. That way you can tell quickly whether the work is right without redoing it. The transcript already shows tool activity, computer use, created files, questions, and approval requests, and evidence helps you find what matters in all of that.

One point is easy to miss: memory isn't a substitute for an authoritative source. The docs advise keeping changing facts in the source system, asking the Bot to cite or reopen current data for decisions that matter, and correcting stale assumptions directly. State lasting preferences explicitly. For keeping memory in shape, see [Issue 6](/issues/2026-11-06/).

::: prompt
When you're done, please include:
1. A link to every source you used.
2. Screenshots of the key pages.
3. An action log of ten lines or fewer saying what you changed and what you didn't.
For any conclusion with numbers, reopen the current data to check it rather than relying on memory.
:::

### Tip 4: Change direction, and use threads and reactions {#tip4}

When plans change, you don't have to wait for the Bot to finish. The docs say a direct message from you takes priority over background work and can redirect the current turn. When work should end right away, send a direct "Stop now". Actions already completed aren't undone.

As a conversation grows, these small tools help:

::: steps
- Reply in a thread | Put feedback on one result or one approval request in a thread. The main transcript stays focused, and the context of the decision is kept.
- Reactions | Good for lightweight acknowledgement. Write a reply when the instruction changes, and don't let a reaction alone carry a safety-critical decision.
- New thread or new Bot | When a conversation has turned into a different long-lived job, start a thread or create a new Bot for it.
:::

::: prompt
Pause the direction you were going in. The new priority is [new request].
Tell me which actions you've already completed and which haven't started yet,
and how you plan to proceed under the new request. Wait for my OK before continuing.
:::

### Tip 5: Find past work with search {#tip5}

If you can't find a file or a message from your Bot last week, you don't need to scroll back through the chat. On desktop, the search palette lets you:

::: props
- Switch: Move between Bots and groups
- Messages: Find prior messages across chats
- Results: Find files, links, and routines
- Settings: Open settings and common actions
- Jump back: Return to the matching place in a conversation
:::

Press `Cmd/Ctrl+K` for the search palette, `Cmd/Ctrl+Shift+F` to search Bots, and `Cmd/Ctrl+F` to find in the current chat. When the results say **Searched recent messages**, choose **Search older** to look further back. Select some text and press `Cmd/Ctrl+L` to add it to the chat and ask a follow-up.

::: prompt
Last week you made me [the result, for example: a competitor pricing comparison].
Find that file and the conversation it came from, and tell me how recent its data is.
Then update it with current data and list what changed.
:::

## Boundaries you should know {#limits}

::: props
- Stopping isn't undoing: "Stop now" ends the work still to come; actions already completed aren't reversed
- Approving isn't undoing: An approval controls the proposed action and doesn't reverse work already completed
- Reactions aren't instructions: Use reactions for light acknowledgement and write out any safety-critical decision
- Memory isn't a source: The source system is the authority for important facts, and safety boundaries rely on approvals and Auto Review rules, not memory alone
- Your Bot takes initiative, but asks first: Your primary Bot offers to take on work it spots, and it asks before risky actions
:::

## Case study: a fictional event planner turns a one-line request into one that works the first time {#case}

A fictional scenario (not anyone's real setup): an event planner asks a Bot to help prepare next month's in-person meetup. Her first message is just "help me get ready for the meetup", and the Bot needs several rounds of questions to work out what she wants.

::: props
- Starting point: A one-line request with no sources and no boundaries
- Goal: Hand off the work clearly once and get back a planning checklist she can use as is
- Concern: She doesn't want the Bot sending invitations to speakers on its own
:::

### Highlights: four parts, boundaries, evidence, and a change of direction {#case-flow}

::: steps
- Rewrite the request | Following Tip 1, she states the result (a planning checklist), the source (a link to the venue quotes doc), the limits (a budget cap and the date), and when to check with her.
- Set the boundary | Following Tip 2, she adds: draft the invitations but don't send them, and show her the list and the text before anything goes out.
- Ask for evidence | She asks for a link to the quote source for each venue and a short action log at the end.
- Change direction | Halfway through, the date moves. She sends a new message with the new date, and the Bot reports what it has finished before adjusting to the new date.
:::

::: prompt
I'm preparing [event name]. Please return a planning checklist with three parts: venue, materials, and speaker invitations.
Use only [doc link], with a budget cap of [amount] and a date of [date].
Draft the invitations but don't send them. Show me the list and the text before anything goes out.
Include a link to the quote source for each venue, and end with a short action log.
:::

## Community picks: small habits for talking to your Bot {#community}

This issue collects a few ways to talk to your Bot. The first three come from explanations and advice in the official docs. The last three are extensions built on the official docs, offered for reference.

### One thread for each long-lived job {#c1}

The docs suggest starting a thread or a new Bot when a conversation has turned into a different long-lived job. With one job per conversation, the Bot is less likely to mix up context.

### Dictate, then edit before sending {#c2}

On desktop, press `Cmd/Ctrl+D` in the composer to dictate. Your speech turns into text first, so you can read it, edit it, and then send. It's the fastest way to get a rough request down.

### Name things with @ {#c3}

Using `@` to mention a Bot, group, routine, or app in your message is more precise than describing "the task that runs every morning".

### A fixed three-line ending {#c4}

End the prompts you use often with the same three lines: include source links, include an action log, and list what not to do. Once it's a habit, you'll redo less work.

### Have the Bot restate the task first {#c5}

For a complex task, ask the Bot to restate the goal and the boundaries in a few sentences before it starts. If it got something wrong, one sentence fixes it, which is far cheaper than redoing finished work.

### When correcting, say "from now on" {#c6}

When your Bot gets something wrong, point out the problem this time and also say clearly that it should work this way from now on. The docs advise correcting lasting preferences explicitly, so you don't have to repeat yourself.
