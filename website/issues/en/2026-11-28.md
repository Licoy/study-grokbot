## What this issue covers {#intro}

When [Issue 2](/issues/2026-11-02/) introduced routines, its last tip briefly mentioned letting events wake your Bot. Many people later found that this one tip saves the most time and usage: instead of having the Bot check every hour whether anything is new, wait until something actually happens, then let it start.

This issue covers the parts of the official "Skills and routines" page about event triggers, testing, managing, and limits, in five tips plus a few real projects from the community. For writing schedules and choosing a time zone, see Issue 2.

::: callout The one thing to remember
Wait for events instead of polling. Keep triggers narrow and guard the webhook key like a password. A 200 only means work started, so look for the result in the chat. Test before you rely on a routine, then watch your usage and the run limits.
:::

One thing up front: Cursor account integrations start these routines. They're separate from the Slack or GitHub apps and may need their own connection. Also, only new activity counts: messages and events from before the trigger existed don't start a run.

## Five tips you can use today {#tips}

Each tip comes with an example prompt. Replace the parts in square brackets with your own and send it.

### Tip 1: Keep Slack triggers narrow, in channel and phrase {#tip1}

A Slack trigger can start a routine in these cases, and it can watch one channel or all of Slack:

::: steps
- The Bot is mentioned | Someone mentions the Bot in a message.
- A word or phrase | A message contains a word or phrase you pick.
- A reaction | You react to a message.
- Any message | Any new message arrives in the channel.
:::

The official advice is clear: keep the channel and phrase narrow. A trigger on any message in a busy channel runs often, spends usage on messages that don't need the Bot, and makes it more likely to act on irrelevant input. Once it's set up, open the routine and check **When to run**, which shows the trigger in words, such as a phrase and a channel.

::: prompt
Set up a routine: when a message in [channel, e.g. #customer-escalations] contains both a ticket link and the phrase "[phrase, e.g. needs repro]",
open the ticket, put together the repro steps and related logs, and send them to me in this conversation.
Never post anything back to Slack without my approval. When it's set up, send me the exact When to run text so I can check it.
:::

### Tip 2: The three webhook fields, explained {#tip2}

To let another system wake your Bot (a form, a monitor, a small script of your own, or a phone shortcut), use a webhook. First ask the Bot to add a webhook trigger to the routine, then open the routine on desktop. The **Webhook** section shows three fields, and you click one to copy it:

::: props
- POST to: The URL to call
- key: The secret; senders include it as `Authorization: Bearer <key>`
- header: That full header, ready to copy
:::

Send an HTTP POST to that URL with the header and, optionally, a JSON body. The Bot receives the body along with the routine instruction. The simplest test call looks like this (replace the angle-bracket parts with what you copied):

```bash
curl -X POST "<the POST to URL>" \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"order_id": "A1024", "event": "refund_requested"}'
```

The key is what opens this door. Keep it only in the sender's settings, and never paste it into a group chat, a public repository, or a screenshot.

::: prompt
Set up a routine that a webhook starts. On each call, read [fields, e.g. order_id and event] from the request body,
look up that [item, e.g. order], and give me a note of three lines or fewer in this conversation with a suggested next step.
If the body is missing a field or is malformed, tell me what's missing instead of guessing. When it's set up, tell me what the body should look like.
:::

### Tip 3: Read a 200 correctly, and look for the result in the chat {#tip3}

A `200` response to a webhook call means Grok Bot accepted the call and started a run. It does **not** mean the Bot has finished. The result shows up in the Bot's chat.

Any other response means a run didn't start. The docs point to just two checks:

::: steps
- Paused? | The routine isn't **Paused**; on the phone, **Active** is on.
- Current key? | The request uses the current key, not an old one.
:::

So the sender only needs to care whether it got a 200, and shouldn't wait for the Bot's result. If the result needs to go somewhere else, say in the routine instruction where it goes and in what form, and keep the "ask me first before sending" boundary.

::: prompt
Check your webhook routine [routine name]:
Is it paused or active right now? What happened on its last few runs?
If any failed, list the reasons and tell me whether I need a new key.
:::

### Tip 4: Test before you rely on it, then read the run history {#tip4}

If the routine shows **Test**, use it after creating or editing the routine: open the routine on desktop and choose **Test**. The button says **Running…** until the run finishes, and the result shows up in the Bot's chat. If the test can't start, you see **Couldn't start a test run**, or a message that explains why. Some routines don't show **Test**. For those, ask the Bot to do the same work once in chat with a safe input, then check the first real run.

Keep in mind that a test run performs real work: it can navigate websites, change files, and call connected tools. Use safe inputs and keep write actions behind approval. Afterward, go through the official checklist:

::: steps
- Inputs | Did it select current inputs?
- Format | Does the output meet the required format?
- Trail | Does every action have a source or audit trail?
- Boundary | Did it stop at the intended approval point?
- Failure | Are failure states explicit?
:::

Once it's running, open the Bot's profile on the phone and tap a routine under **Routines** to see **Active**, **Schedule**, **Next run**, **Instruction**, and **Run history**. Run history shows each recent run as **Running**, **Succeeded**, or **Failed**, with the reason for a failed run. **No runs yet** means nothing has started the routine yet.

::: prompt
I just set up [routine name]. First run it once with this safe test input: [test input, e.g. a fake ticket link].
Then report back on: which inputs you used, whether the output format is right, which actions you took, where you stopped for my approval, and whether anything failed.
Don't send, buy, delete, or publish anything during the test.
:::

### Tip 5: Watch the run limits and your usage {#tip5}

Routines have a few hard limits worth knowing before you design one:

::: props
- Per Bot: Up to 50 routines
- Run records: The 20 most recent for each routine
- Schedules: At least five minutes apart
- Per hour, all routines: Up to 300 runs
- Per hour, one routine: Up to 200 runs
:::

A run past either hourly limit fails with `Automation run rate limit exceeded`. The docs add that some runs can fail with this error because of a limit all Grok Bot routines share, even when your own routines run less than that. This is a known issue that is being fixed. These failed runs are **not retried automatically**, so rerun them yourself: use **Test** to run it now, or for a webhook, send the call again.

As for usage, each run spends usage, so a routine that runs often spends more. The docs put it this way: an hourly schedule, a short interval, or a Slack trigger on a busy channel can use a week of usage in a day. A routine that never runs doesn't spend usage, but **Test** does, because it performs the work. Also, after a long period away, Grok Bot may ask whether to keep your routines running and pause them if you don't respond, so review paused routines when you return.

::: prompt
List every routine you own: what starts it, about how often it runs, and whether it has failed recently.
Mark the ones that run most often, and suggest which could have a wider schedule, a narrower Slack trigger, or a webhook trigger instead.
List the suggestions first, and wait for my OK before changing anything.
:::

## Limits you should know {#limits}

::: props
- New activity only: Messages and events from before the trigger existed don't start a run
- A trigger isn't the app: A Slack trigger is separate from the Slack app; connect Slack on the Cursor account that owns the Bot first
- 200 isn't done: A 200 from a webhook only means a run started; the result is in the Bot's chat
- Test does real work: A test run takes real actions and spends usage
- Deleting is final: Deleting a routine stops its future runs and can't be undone; deleting a Bot also removes the routines it owns
- Team Bots: Right-click a routine to set **Who can use this routine?**: **Only me** keeps it to yourself, and **Everyone with access** runs it for everyone who can use the Bot
:::

The official principles for designing routines are worth copying too: automate preparation before execution; have the Bot draft, reconcile, or recommend first; require approval for sending, purchasing, deleting, publishing, or changing production systems; include a no-data and stale-data policy; make retries idempotent where possible; tell the Bot where to report partial completion; and re-test after a website, app, or source format changes.

## Case study: a fictional online shop moves from hourly polling to events {#case}

A fictional scenario (not anyone's real setup): the owner of a small online shop had a Bot check every hour for new refund requests. Over a week it spent a fair amount of usage, yet when a request did arrive, it could sit for most of an hour.

::: props
- Starting point: A routine that checks for refunds every hour
- Goal: Handle a refund request as soon as it arrives, and run zero times when there are none
- Concern: Replies to customers and refunds must be confirmed by the owner
:::

### Highlight: a webhook for events, a Slack trigger for internal asks, approval as the safety net {#case-flow}

::: steps
- Switch triggers | Following Tip 2, ask the Bot for a new webhook routine, and have the shop's back office call it when a refund request comes in, with the order number in the body.
- Internal asks | Following Tip 1, add a Slack trigger that only watches the phrase "Bot, take a look" in #after-sales, not every message.
- Test first | Following Tip 4, run Test with a fake order number and check that the Bot only drafts a reply and stops for approval before any refund.
- Retire the old one | Following Tip 5, once the new flow works, pause the hourly polling routine and watch a week of usage.
:::

::: prompt
Replace my "check for refunds every hour" routine with event triggers:
1. Set up a webhook routine whose body includes order_id. On each call, look up the order, draft a reply to the customer and a refund recommendation, and send them to this conversation for my approval.
2. Tell me the body format, and where I should put the POST to URL and the header.
3. Once the new flow passes a test, pause the old hourly routine. Don't delete it.
Don't message any customer or issue any refund; wait for my approval on everything.
:::

## Community picks: letting events wake the Bot {#community}

This issue collects real setups that users shared on X. Quotes are excerpts from the original posts; follow the links for the full text.

### One text message wakes a routine {#c1}

::: quote @Michael_Fenech_ | 2026-11-10 | https://x.com/Michael_Fenech_/status/2119885990437200101
Grok Bot doesn't need to wait for you to give it instructions anymore. Your iPhone can tell it when to get to work. I tested this today. My wife sent me a simple iMessage containing a keyword. That message automatically triggered my Grok Bot routine
:::

A reply under the post sums it up as a message keyword starting a webhook routine with the real message text. That's Tip 2: when a phone automation sees a message with the keyword, it calls the routine's webhook URL and puts the message in the body.

### Talk to the TV, and the Bot plays a video {#c2}

::: quote @MarcoPorro | 2026-10-31 | https://x.com/MarcoPorro/status/2116500940983296031
How: the TV calls my own Grok Bot webhook routine, which replies via ntfy. Works with the PC off.
:::

Routines run in the cloud, so the device making the call only needs to send an HTTP request. Whether the computer at home is on doesn't matter.

### A muted channel, read 1,900 times a week {#c3}

::: quote @0xMfox | 2026-11-02 | https://x.com/0xMfox/status/2117276687612145753
My Grok Bot was reading a Slack channel I muted 1900 times a week. That's why my limit died every Wednesday. I found it by asking the bot itself.
:::

This is exactly what Tips 1 and 5 guard against: a trigger that's too broad. The fix starts the same way, by asking the Bot to list its own routines, as in the Tip 5 prompt.

### Wake up the moment new email arrives {#c4}

::: quote @AgentMsgr | 2026-11-12 | https://x.com/AgentMsgr/status/2120629790436983252
Grok Bot sits on new email until you open the app. One webhook routine fixes it.
:::

The author has the inbox call a webhook routine when new mail arrives. If the mail goes to the Bot's own address, an email to that address is already a built-in trigger; see [Issue 10](/issues/2026-11-10/).
