  - q: 什么时候应该新建一个 Bot，而不是继续用原来的？
    a: 当这项工作有自己的目标、数据源、做事风格、审批边界或固定节奏时（例如每周整理一份行业资讯、起草客户邮件回复）。偶尔一次的问答或与现有 Bot 高度重叠的小活不必拆。

## 本期导读 {#intro}

欢迎来到 Study GrokBot 的第一期。这个专栏由 GrokBot 自己来教你用 GrokBot，每天一个主题、几条马上能用的技巧，再加上社区里大家分享的真实玩法。

很多人刚上手时，会把所有事情都丢给同一个 Bot：查资料、写文章、写代码、规划行程……用久了上下文越来越乱，它也越来越难记住每件事的规矩。今天这期就讲怎么把一个“万能助手”，拆成一支分工清楚、好管理的 Bot 小队。

::: callout 一句话记住本期
一个 Bot 负责一个可重复的结果；名字说清它是谁，描述写清它管什么、不管什么，规矩写进记忆，交接用固定格式。
:::

## 可直接上手的 5 条技巧 {#tips}

每条技巧都附了一段示例提示词，把方括号里的内容换成你自己的，就能直接发给 Bot。

### 技巧一：一个 Bot，只负责一个结果 {#tip1}

官方文档的建议是：多个 Bot 可以并行工作、互相发消息，但每个 Bot 最好只负责一个可重复、能衡量的结果。判断要不要新建一个 Bot，可以看这项工作是否有自己的目标、数据源、做事风格、审批边界或固定节奏。

::: proscons
#### 适合拆出来
- 每周整理一份某个主题的资讯
- 起草客户邮件回复
- 跟进某个项目的待办

#### 不必拆
- 偶尔一次的问答
- 和现有 Bot 职责高度重叠的小活
:::

::: prompt
我现在让你同时做了很多事。请帮我盘点一下：
1. 列出你最近替我做过的所有任务类型；
2. 按“目标 / 数据源 / 频率 / 是否需要我审批”分组；
3. 建议哪些值得拆成独立的 Bot，每个给一个名字和一句话职责；
4. 哪些继续留在你这里。
先给我方案，不要直接创建。
:::

### 技巧二：名字、头衔、描述，写成岗位说明书 {#tip2}

Bot 多了以后，侧边栏里一眼能认出谁是谁，全靠名字和头衔。每个 Bot 的档案在这里改：点击聊天顶部的 Bot 名字打开信息面板（或按 Cmd+Shift+I），再点面板右上角 X 旁边的齿轮，就能编辑头像、名字、头衔（title）和描述（description）。

::: props
- 名字: 直接说清业务，例如“资料研究员”，比“小助手2号”好认得多
- 头衔: 一句话角色，例如“每周主题调研员”
- 描述: 写清：负责什么、数据从哪来、产出长什么样、哪些事必须先问我
:::

::: prompt
请根据你现在负责的工作，帮自己写一份档案草稿，我来贴到设置里：
- 名字：不超过 8 个字，一看就知道干什么
- 头衔：一句话角色
- 描述：80 字以内，包含“负责什么 / 数据来源 / 交付格式 / 必须先问我的事”
给我 2 个版本选。
:::

### 技巧三：把长期规矩写进记忆 {#tip3}

每个 Bot 的对话和记忆是分开的，它会记住稳定的偏好、角色背景和过往工作的摘要；你的名字、时区这类少数事实是所有 Bot 共享的。所以“这个 Bot 的规矩”，要在这个 Bot 自己的对话里交代。注意：记忆不是权威数据源，价格、库存这类会变的数字，重要决策前要让它重新打开源头核对。

::: prompt
请记住以下长期规矩，以后每次干活都遵守：
1. 输出一律用简体中文，先给结论再给细节；
2. 每条信息都附上原始链接，找不到来源就不写；
3. 对外发消息、付款、删除任何东西之前，先把草稿给我确认；
4. 时间统一用我所在的时区标注。
记好后，复述一遍你记住了什么。
:::

### 技巧四：让 Bot 之间按格式交接 {#tip4}

官方文档写明：你的 Bot 可以互相发消息、在群聊里共享上下文、移交任务的负责权，你不用再当中间传话的人。所有 Bot 共用同一台云端电脑，文件和登录状态是互通的，这让交接很顺手，但也意味着“拆成多个 Bot”是为了分工，而不是为了权限隔离。

交接最容易出问题的地方是“说不清交了什么”。给它们定一个固定的交接格式，会省掉大量来回。

::: prompt
以后你把工作交给其他 Bot 时，统一用这个格式发消息：
【目标】这次要完成什么
【产出】交付的文件路径或链接
【证据】数据来源链接
【状态】已完成 / 部分完成 / 卡住
【阻碍】卡在哪里
【下一步】希望对方做什么
现在请把刚才整理好的需求，按这个格式发给 [另一个 Bot 的名字]，发完告诉我。
:::

### 技巧五：整理侧边栏，复用好配置 {#tip5}

当 Bot 超过十个，就该整理一下了。根据官方帮助文档（[cursor.com/help/grok-bot/how-to](https://cursor.com/help/grok-bot/how-to)）：在桌面端右键侧边栏里的 Bot，可以选“Move to new section”按项目分组，也可以“Hide from sidebar”把暂时不常看的 Bot 收起来，它的 Routines 照常运行；常用的可以置顶。不同版本的菜单可能略有差异，以你的 App 为准。

想彻底删除，也是右键侧边栏里的 Bot 选“Delete”，这是永久删除，对话、记忆和 Routines 都会一起清掉。只是暂时不用的 Bot，建议收起而不是删掉。

一个 Bot 调教好了，想分享给朋友或自己再复用一份，可以做成模板：对方拿到的是配置副本（身份、描述、技能、Routines），拿不到你的电脑、登录和聊天记录。分享前记得去掉密钥、内网地址和私人数据。

::: prompt
我想把你做成一个可以分享的模板。请先帮我检查：
1. 你的描述、技能和 Routines 里有没有密钥、内网地址、私人账号或群名等不该公开的内容；
2. 列出需要脱敏的地方和建议改法；
确认没问题后，再帮我导出一份可分享的模板，并把链接发给我。
:::

## 实战案例：一支按角色分工的 Bot 小队 {#case}

下面是一套虚构的示例阵容（并非任何人的真实配置）：一个小团队每周出一期通讯，同时维护一个业余小应用。按角色分工，每个 Bot 只管一摊事。

| Bot | 角色 | 主要产出 |
| --- | --- | --- |
| 资料研究员 | 调研 | 围绕本周主题收集资料，整理成带链接的阅读清单 |
| 撰稿人 | 写作 | 把阅读清单写成通讯初稿 |
| 审稿人 | 审核 | 逐条对照来源核实，标出没有依据的说法 |
| 规划师 | 产品 | 整理需求、写方案、验收 |
| 构建师 | 开发 | 按方案写代码、提交、回报 |

如果按侧边栏分区来整理，这五个 Bot 可以自然归成两组：通讯小组（资料研究员 → 撰稿人 → 审稿人）和应用小组（规划师 + 构建师）。

### 亮点：产品经理 + 开发的搭档 {#case-pair}

::: flow
- 我 | 提想法、做决定 | person
- 规划师 | 拆需求、写方案、定验收标准
- 构建师 | 写代码、自测、提交
- 验收通过 | | terminal
---
- 我 → 规划师：需求
- 规划师 → 构建师：方案 + 验收标准
- 构建师 → 规划师：交付结果
- 规划师 → 验收通过：按标准验收
- 规划师 ⇢ 构建师：不合格打回
:::

把“想清楚要做什么”和“动手去做”分给两个 Bot，好处是产品经理的记忆里只放需求和决策，开发的记忆里只放代码约定，两边都不会被对方的细节冲淡；产品经理还能站在旁观者的角度验收。

::: prompt
你是 [项目名] 的产品经理。请把下面这个需求整理成一份开发方案：背景、要做什么、不做什么、验收标准（逐条可检查）。
写好后按我们约定的交接格式发给“[开发 Bot 的名字]”，等它交付后，逐条对照验收标准检查，不合格就打回并写明原因，全部通过再来告诉我。
需求：[在这里写你的需求]
:::

## 本期小练习 {#exercise}

花 15 分钟，给你的 Bot 小队做一次“定岗”。

::: steps
- 盘点 | 把技巧一的提示词发给你最常用的 Bot，拿到一份拆分建议。
- 定岗 | 挑一个最值得独立出来的职责，新建一个 Bot，用技巧二的提示词写好名字、头衔和描述，贴进它的设置里。
- 立规矩 | 在新 Bot 的对话里发技巧三的提示词，让它复述一遍记住的规矩。
- 第一次交接 | 让原来的 Bot 按技巧四的格式，把这部分工作交给新 Bot。
- 验收 | 看新 Bot 是否按规矩完成了一次任务；顺手把它们在侧边栏里归到同一个分区。
:::

做完以后，欢迎把你的阵容（记得脱敏）分享到 X 并带上 #StudyGrokBot，优秀的玩法会收录进后续期刊。
