## 本期导读 {#intro}

[第 2 期](/zh/issues/2026-11-02/)讲例行任务入门时，用最后一条技巧简单提了一句“让事件叫醒 Bot”。不少人后来发现，真正省心又省用量的，恰恰是这一条：与其让 Bot 每小时去看一眼有没有新东西，不如等事情真的发生了，再让它开工。

本期把官方文档“技能与例行任务”一页里关于事件触发、测试、管理和限额的部分完整展开，整理成 5 条技巧，再配上社区里几个真实的玩法。时间表怎么写、时区怎么选，见第 2 期。

::: callout 一句话记住本期
能等事件就别轮询；触发条件要窄，Webhook 的 key 当密码保管；200 只是“已开工”，结果去对话里看；上线前先 Test，跑起来盯住用量和次数上限。
:::

有一点先说在前面：事件触发由 Cursor 账号的集成来启动，和 Slack、GitHub 应用是两回事，可能需要单独连接一次。另外，只有触发器建好之后发生的新动静才算数，之前的旧消息、旧事件不会补跑。

## 可直接上手的 5 条技巧 {#tips}

每条技巧都附了一段示例提示词，把方括号里的内容换成你自己的，就能直接用。

### 技巧一：Slack 触发器，频道和短语都要窄 {#tip1}

Slack 触发器可以在以下几种情况下启动例行任务，范围可以是一个频道，也可以是整个 Slack：

::: steps
- Bot 被提到 | 有人在消息里提到这个 Bot。
- 词或短语 | 消息里出现你指定的某个词或短语。
- 表情回应 | 你给某条消息加了表情回应。
- 任意消息 | 频道里来了任何一条新消息。
:::

官方的建议很明确：频道和短语都要窄。盯着热闹频道的“任意消息”会跑得很频繁，花掉大量用量，还更容易让 Bot 对无关内容动手。设好之后，打开例行任务看 **When to run**，它会用文字写出触发条件，比如某个短语加某个频道。

::: prompt
帮我建一个例行任务：当 [频道名，例如：#客户升级] 里出现一条消息，同时包含工单链接和短语“[短语，例如：需要复现]”时，
打开这张工单，整理出复现步骤和相关日志，在这个对话里发给我。
没有我的同意，不要往 Slack 里回任何消息。建好后把 When to run 的原文发给我核对。
:::

### 技巧二：Webhook 三个字段，一次讲清 {#tip2}

想让别的系统（表单、监控、自己写的小脚本、手机快捷指令）叫醒 Bot，就用 Webhook。先请 Bot 给例行任务加一个 Webhook 触发器，再到桌面端打开这个例行任务，**Webhook** 区域里有三个字段，点一下就能复制：

::: props
- POST to: 调用地址
- key: 密钥，调用方要放在请求头 `Authorization: Bearer <key>` 里
- header: 上面那个完整的请求头，直接复制就能用
:::

调用方式是向这个地址发一个 HTTP POST，带上请求头，可以附一个 JSON 请求体；Bot 会连同例行任务的指令一起收到这个请求体。一个最简单的测试调用长这样（尖括号里换成你复制的内容）：

```bash
curl -X POST "<POST to 的地址>" \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"order_id": "A1024", "event": "refund_requested"}'
```

key 相当于这扇门的钥匙，只放在调用方的配置里，别贴进群聊、公开仓库或截图。

::: prompt
帮我建一个由 Webhook 触发的例行任务：每次收到调用时，读取请求体里的 [字段，例如：order_id 和 event]，
查清这笔 [业务对象，例如：订单] 的情况，在这个对话里给我一段三行以内的说明和建议的下一步。
请求体缺字段或格式不对时，直接告诉我缺了什么，不要猜。建好后告诉我请求体应该长什么样。
:::

### 技巧三：读懂 200，结果去对话里找 {#tip3}

Webhook 调用返回 `200`，意思是 GrokBot 已经接收了这次调用、开始了一次运行，**不是** Bot 已经做完。结果会出现在 Bot 的对话里。

返回的不是 `200`，就说明这次没有启动运行。官方给的排查方向只有两条：

::: steps
- 是否暂停 | 例行任务没有处于 **Paused**；手机上 **Active** 是打开的。
- key 是否最新 | 请求里用的是当前的 key，不是旧的。
:::

所以调用方只需要关心“是否返回 200”，不要让它等 Bot 的处理结果。需要把结果再送到别处时，在例行任务的指令里写清楚送到哪、以什么形式，并保留“需要我同意再发”的边界。

::: prompt
检查一下你的 [例行任务名] 这个 Webhook 例行任务：
它现在是暂停还是运行中？最近几次运行分别是什么结果？
如果有失败的，列出失败原因，并告诉我是不是需要换新的 key。
:::

### 技巧四：上线前先 Test，跑起来看运行记录 {#tip4}

例行任务显示 **Test** 时，建好或改完都先测一次：在桌面端打开例行任务，选 **Test**。按钮会显示 **Running…** 直到跑完，结果出现在 Bot 的对话里；启动不了会显示 **Couldn't start a test run** 或说明原因。有的例行任务不显示 **Test**，那就先在对话里用安全的输入让 Bot 手动做一遍，再盯一下第一次正式运行。

注意，测试运行做的是真实的工作：会打开网站、改文件、调用连接的工具。所以要用安全的输入，写操作一律放在审批之后。测完对照官方的检查清单：

::: steps
- 输入 | 用的是不是最新的数据？
- 格式 | 输出符不符合要求的格式？
- 留痕 | 每个动作有没有出处或记录？
- 边界 | 有没有在该停下等审批的地方停下？
- 失败 | 出错时有没有明确说出来？
:::

跑起来以后，手机上打开 Bot 的资料页，在 **Routines** 里点进某个例行任务，可以看到 **Active**、**Schedule**、**Next run**、**Instruction** 和 **Run history**。运行记录会显示每次是 **Running**、**Succeeded** 还是 **Failed**，失败的会写原因；显示 **No runs yet** 就是还没被触发过。

::: prompt
我刚建好 [例行任务名]。请先用一份安全的测试输入 [测试输入，例如：一条假工单链接] 跑一遍，
跑完按这几点给我报告：用了哪些输入、输出格式对不对、做了哪些动作、在哪里停下等我审批、有没有出错。
测试期间不要发送、购买、删除或发布任何东西。
:::

### 技巧五：盯住次数上限和用量 {#tip5}

例行任务有几条硬性限制，最好在设计时就心里有数：

::: props
- 每个 Bot: 最多 50 个例行任务
- 运行记录: 每个例行任务保留最近 20 条
- 定时间隔: 至少相隔 5 分钟
- 每小时合计: 你所有的例行任务加起来每小时最多跑 300 次
- 每小时单个: 单个例行任务每小时最多跑 200 次
:::

超过任何一个上限，这次运行会失败，报错 `Automation run rate limit exceeded`。官方还说明，有时即使你自己没跑这么多，也会因为所有例行任务共用的一个上限而报同样的错，这是已知问题，正在修复。这类失败**不会自动重试**，需要你自己重跑：用 **Test** 立刻跑一次，Webhook 的话就重新发一次调用。

用量方面，每次运行都花用量，跑得越勤花得越多。官方原话的意思是：每小时一次的时间表、很短的间隔，或者盯着热闹频道的 Slack 触发器，可能一天就用掉一周的用量。从没运行过的例行任务不花用量，但 **Test** 会花，因为它做的是真实工作。另外，你很久没回来时，GrokBot 可能会问你要不要让例行任务继续跑，没回复就会把它们暂停，回来后记得看看哪些被暂停了。

::: prompt
帮我盘点一下你名下所有的例行任务：每个是什么触发的、大概多久跑一次、最近有没有失败。
标出跑得最勤的几个，建议哪些可以放宽时间表、收窄 Slack 触发条件，或者改成 Webhook 触发。
先列建议，等我确认后再改。
:::

## 几个必须知道的边界 {#limits}

::: props
- 只认新动静: 触发器建好之前的消息和事件不会启动运行
- 触发器不是应用: Slack 触发器和 Slack 应用是两回事，要先在拥有这个 Bot 的 Cursor 账号上连接 Slack
- 200 不等于完成: Webhook 返回 200 只代表已开始运行，结果在 Bot 的对话里
- Test 是真干活: 测试运行会做真实操作，也会花用量
- 删除不可撤销: 删除例行任务会停止之后的所有运行，无法撤销；删除 Bot 也会删除它名下的例行任务
- 团队 Bot: 右键例行任务可以设置 **Who can use this routine?**，选 **Only me** 只给自己用，选 **Everyone with access** 给所有能用这个 Bot 的人用
:::

官方给例行任务的设计原则也值得抄下来：先自动化准备工作，再考虑执行；让 Bot 先起草、核对或给建议；发送、购买、删除、发布或改动生产系统一律要审批；写清没有数据和数据过期时怎么办；重试尽量做到重复执行也不出错；告诉 Bot 只完成一部分时向哪里汇报；网站、应用或数据格式变了之后要重新测试。

## 实战案例：虚构的网店客服，从每小时轮询换成事件触发 {#case}

一个虚构的场景（并非任何人的真实配置）：一家小网店的店主，原来让 Bot 每小时查一遍有没有新的退款申请，一周下来用量花了不少，真正有事的时候却要等上大半小时。

::: props
- 起点: 一个每小时运行的“查退款”例行任务
- 目标: 退款申请一来就处理，没申请时一次都不跑
- 顾虑: 回复顾客和退款都必须由店主本人确认
:::

### 亮点：Webhook 接事件，Slack 触发器接内部求助，审批兜底 {#case-flow}

::: steps
- 换触发方式 | 按技巧二，请 Bot 新建一个 Webhook 例行任务，让网店后台在有退款申请时调用它，请求体里带上订单号。
- 内部求助 | 按技巧一，再建一个 Slack 触发器，只盯 #售后 频道里的短语“请 Bot 看看”，不盯任意消息。
- 先测再上 | 按技巧四，用一个假订单号 Test 一遍，确认 Bot 只起草回复、在退款前停下等审批。
- 停掉旧的 | 按技巧五，确认新流程能跑以后，暂停原来那个每小时轮询的例行任务，再观察一周用量。
:::

::: prompt
帮我把“每小时查一次退款”换成事件触发：
1. 新建一个 Webhook 例行任务，请求体里会带 order_id；收到后查清订单情况，起草一封给顾客的回复和退款建议，发到这个对话里等我确认；
2. 告诉我请求体的格式，以及我该把 POST to 和 header 填到哪里；
3. 新流程测试通过后，先暂停原来那个每小时的例行任务，不要删除。
不给顾客发任何消息、不执行退款，全部等我批准。
:::

## 社区玩法精选：让事件来叫醒 Bot {#community}

本期整理了几位用户在 X 上分享的真实玩法。引文为原帖的中文译文，原文请看原帖链接。

### 一条短信，叫醒例行任务 {#c1}

::: quote @Michael_Fenech_ | 2026-11-10 | https://x.com/Michael_Fenech_/status/2119885990437200101
Grok Bot doesn't need to wait for you to give it instructions anymore. Your iPhone can tell it when to get to work. I tested this today. My wife sent me a simple iMessage containing a keyword. That message automatically triggered my Grok Bot routine
---
Grok Bot 不必再等你下指令了，你的 iPhone 可以告诉它什么时候开工。我今天试了：我妻子给我发了一条带关键词的 iMessage，这条消息自动触发了我的 Grok Bot 例行任务。
:::

这条帖子下的回复把它概括为：用短信里的关键词启动一个 Webhook 例行任务，并把短信原文一起传进去。思路正是技巧二：手机上的自动化收到带关键词的短信后，向例行任务的 Webhook 地址发一次调用，把消息内容放进请求体。

### 对电视说一句话，Bot 就去放视频 {#c2}

::: quote @MarcoPorro | 2026-10-31 | https://x.com/MarcoPorro/status/2116500940983296031
How: the TV calls my own Grok Bot webhook routine, which replies via ntfy. Works with the PC off.
---
做法：电视调用我自己的 Grok Bot Webhook 例行任务，结果再通过 ntfy 推送回来。电脑关着也能用。
:::

例行任务在云端运行，所以发起调用的设备只要能发 HTTP 请求就行，家里的电脑开不开都没关系。

### 静音的频道，一周被读了 1900 次 {#c3}

::: quote @0xMfox | 2026-11-02 | https://x.com/0xMfox/status/2117276687612145753
My Grok Bot was reading a Slack channel I muted 1900 times a week. That's why my limit died every Wednesday. I found it by asking the bot itself.
---
我的 Grok Bot 一周读了 1900 次一个我早就静音的 Slack 频道，这就是我的额度每到周三就用完的原因。我是直接问 Bot 自己才查出来的。
:::

这正是技巧一和技巧五要防的情况：触发条件太宽。查的方法也很简单，直接让 Bot 盘点自己的例行任务，像技巧五的示例提示词那样。

### 新邮件一到，立刻叫醒 {#c4}

::: quote @AgentMsgr | 2026-11-12 | https://x.com/AgentMsgr/status/2120629790436983252
Grok Bot sits on new email until you open the app. One webhook routine fixes it.
---
在你打开应用之前，Grok Bot 会把新邮件晾在那里。一个 Webhook 例行任务就能解决。
:::

作者的做法是让邮箱在收到新邮件时调用 Webhook 例行任务。如果邮件是发到 Bot 专属邮箱的，官方本身就支持把“收到邮件”作为触发条件，见[第 10 期](/zh/issues/2026-11-10/)。
