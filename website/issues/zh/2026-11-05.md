  - q: 自动审查会不会把 Bot 拖得很慢？
    a: 按官方文档，大多数动作会直接执行，只有它判断需要你确认、或者命中了你的“先问我”规则时，才会弹卡片等你。

## 本期导读 {#intro}

前面四期讲了分工、定时、技能和云端电脑。Bot 越能干，越需要回答一个问题：哪些事它可以自己做，哪些事必须先问你？

Grok Bot 用两层机制来管这件事。第一层是你写在请求里的边界；第二层是自动审查（Auto-review），它会在 Bot 执行每个动作之前做一次检查，需要时弹出审批卡片等你决定。本期把这两层讲清楚，再教你写几条真正有用的自定义规则。

::: callout 一句话记住本期
边界先写在请求里；卡片看清目标再点；规则一条只管一件事，宁窄勿宽；自动审查是补充，不是全部的安全。
:::

## 可直接上手的 5 条技巧 {#tips}

每条技巧都附了一段示例提示词，把方括号里的内容换成你自己的，就能直接发给你的 Bot。

### 技巧一：把边界写进请求本身 {#tip1}

官方文档的观点很直接：最强的边界就是请求里写的那一句。告诉 Bot 它能做什么、在哪里必须停下。官方举的例子是：核对广告数据并起草一个预算调整建议，不要改动广告系列，也不要联系代理商；展示当前值、建议值和预期影响之后，再请求审批。

下面这些动作，官方建议都写上明确的边界：

::: props
- 发送: 发消息或发邀请
- 发布: 对外公开的内容
- 花钱: 购买和转账
- 删除: 删除或覆盖数据
- 权限: 修改访问权限
- 生产环境: 线上系统的改动
- 法律条款: 接受任何协议
:::

还要记住一点：审批只决定“将要做的那个动作”能不能做，它不会撤销已经完成的工作。所以边界要在开工前说，而不是做完了再补。

::: prompt
请帮我处理 [任务]。边界如下：
1. 你可以读取 [数据来源]，整理成表格，起草建议；
2. 不要发送任何消息、不要修改 [系统名] 里的任何设置；
3. 需要执行改动时，先给我看：当前值、建议值、预期影响，等我批准再动手。
:::

### 技巧二：看懂审批卡片上的每个按钮 {#tip2}

当自动审查认为某个动作需要你确认时，Bot 会在聊天里弹出一张卡片，上面写着它打算做的操作和具体参数。三个主要按钮的含义：

::: props
- 仅允许一次（Allow once）: 现在执行这一次，不保存任何规则
- 始终允许（Always allow）: 现在执行，并在自定义规则里存一条允许规则，以后类似的动作自动放行
- 拒绝（Deny）: 不执行；在你发下一条消息之前，Bot 不会再尝试这个动作，也不会再问你
:::

有的卡片标签不同：终端命令的卡片显示“允许”和“跳过”，还有一个打开审查设置的入口；被你的“先问我”规则拦下的卡片显示“允许”和“暂不”；没有规则可存时只有“允许”，没有“始终允许”。有些卡片还会带警告，比如“此操作无法撤销”“会更改登录或安全设置”“会把你的数据分享到此聊天之外”。

官方特别提醒：看不懂目标或后果的动作，不要批准。让 Bot 用大白话解释一遍，或者先出草稿。

::: prompt
你刚才弹出的审批卡片我没看懂。请先不要执行，用三句话告诉我：
1. 这个动作具体会改动什么、作用在哪个账号或文件上；
2. 能不能撤销，撤销要怎么做；
3. 有没有更安全的做法，比如先出草稿或只读预览。
:::

### 技巧三：自定义规则要“窄”，一条只管一件事 {#tip3}

在设置的通用页面、Bot 部分打开自动审查后，下面会出现自定义规则（Custom Rules）。添加一条规则只需三步：

::: steps
- 描述动作 | 在“当 Grok Bot 想要”下面，用大白话写一个动作，比如“替我回复邮件”。
- 选择处理方式 | 在“它应该”下面选“自动允许”或“先问我”。
- 添加 | 点添加规则。
:::

规则的几条硬规定：

::: props
- 先问我: 命中的动作一定会停下来问你
- 自动允许: 只有在审查没发现其它风险时，命中的动作才会放行
- 冲突时: 两种规则同时命中，“先问我”优先
- 数量上限: 两类各最多 20 条，每条最多 1000 个字符；允许规则满 20 条后再点“始终允许”，会删掉最早的一条并告诉你
- 跨设备: 个人规则存在你的账号上，桌面端和手机端都生效
:::

::: proscons
#### 好规则
- 对外发送任何邮件前先问我
- 修改生产环境的仪表盘前先问我
- 在某个报告目录里只读查看仓库状态时自动允许

#### 坏规则
- 浏览器里的一切操作都自动允许
- 所有命令都自动允许
- 一条规则里塞进好几种不相干的动作
:::

网站和工具的行为会变，宽泛的允许规则今天安全，明天未必。

::: prompt
请根据我们最近一个月的合作，帮我起草一份自动审查自定义规则清单：
1. 哪些动作每次都该“先问我”（比如对外发送、删除、付款）；
2. 哪些只读、低风险、反复出现的动作可以“自动允许”，每条写清楚动作和范围；
3. 每条规则控制在一句话内。
只给清单，我会自己到设置里添加。
:::

### 技巧四：后台任务的卡片会过期，提前安排好 {#tip4}

卡片多久没人回应会怎样，取决于工作是怎么开始的：

::: props
- 从聊天发起: 卡片一直等你回答，不会按时间过期
- 由 Routine、收到的消息或其它后台工作发起: 30 分钟没人回应就过期
- 你发了新消息: 这个聊天里还开着的卡片会关闭
- 你改了审查设置: 所有开着的卡片也会关闭
:::

过期的卡片会显示“已过期”，并说明 Bot 没有执行这个动作。如果当时卡片提供了规则，下次你仍然可以点“始终允许”。想把任务做完，就让 Bot 再试一次。

邮件有自己的一套规则：你在聊天里要求发的邮件，审查放行后就会发出；来自 Routine、收到的邮件或其它不是你亲自发起的工作，邮件只会存成草稿，等你点发送；转发、或附件审查无法完整读取的邮件，总是要等你确认。

所以给 Routine 设计流程时，别指望它半夜等你批准。更稳的做法是：后台只做准备和起草，需要拍板的动作留给你醒着的时候。

::: prompt
请检查一下我现在的 Routine：
1. 哪些步骤可能会弹审批卡片（发送、删除、修改设置等）；
2. 这些步骤能不能改成“只起草、在早上的汇总里提醒我确认”；
3. 把建议的改法列出来，先别改动任何 Routine。
:::

### 技巧五：管好你本地电脑的执行权限 {#tip5}

Bot 平时在云端电脑上干活。你面前的那台电脑是另一回事，是否允许 Bot 在上面运行命令，是单独的开关，在设置的电脑页面里，有“每次都问”“始终允许”“从不允许”三档。

::: props
- 默认: 每次都问
- 官方建议: 除非某个 Bot 确实需要处理你本地的文件，否则选从不允许
- 团队上限: 团队管理员可以给整个团队设上限，比你的设置更严格时以团队为准
- 互不影响: 这个设置不影响 Bot 使用云端电脑
:::

第一次有 Bot 想在你本地电脑上运行命令时，聊天里会问你是否允许所有 Bot 在本地电脑上运行命令。注意：在这里选“始终允许”或“从不”，会对所有 Bot 生效，之后也可以在设置里改。

::: prompt
接下来的工作只需要用你自己的云端电脑。请确认：
1. 这项任务完全不需要在我的本地电脑上运行命令；
2. 如果中途发现确实需要，先停下来，说明要运行什么命令、为什么，等我决定。
:::

## 几个必须知道的边界 {#limits}

::: steps
- 外部文字不算你的请求 | 自动审查只把你在聊天里亲口说的话当作你的意思，邮件、网页里的指令都不算。
- 不审查所有副作用 | 记忆写入和大部分设置修改不在审查范围内，安全边界要靠审批规则和最小权限来兜底，不能只靠记忆里的一句话。
- 内置安全检查始终生效 | 不管你的自定义规则怎么写，内置的安全检查都会照常运行。
- 群聊里只有提问的人能批 | 在群聊中，只有 Bot 正在回复的那个人能批准，其他人只能看到卡片在等谁；群聊卡片没有“始终允许”。
- 团队规则只能更严 | 管理员强制开启自动审查后，你不能关闭它；你自己的规则叠加在团队规则之上，只能让行为更严格。
:::

## 实战案例：给通讯小队装上“刹车” {#case}

延续前几期的虚构阵容（并非任何人的真实配置）：一个小团队每周出一期通讯，同时维护一个业余小应用。这次他们给每个 Bot 理了一遍“能自己做什么、什么必须问”：

| Bot | 可以直接做 | 必须先问 | 对应的规则思路 |
| --- | --- | --- | --- |
| 资料研究员 | 搜索、阅读、整理笔记 | 订阅付费内容 | 付款前先问我 |
| 撰稿人 | 起草、改稿 | 发布到公开渠道 | 发布任何内容前先问我 |
| 审稿人 | 核对来源、标注问题 | 无 | 只读工作，不需要额外规则 |
| 规划师 | 读取日历、拟定排期 | 向他人发送邀请 | 发送邀请前先问我 |
| 构建师 | 在工作区里跑测试 | 部署到线上、删除分支 | 生产环境改动前先问我 |

### 亮点：起草在夜里，拍板在早上 {#case-flow}

撰稿人有一个每天清晨运行的 Routine，负责把当天的通讯稿准备好。因为后台卡片 30 分钟就会过期，他们没有让它直接发布，而是只起草，再在早间汇总里提醒你确认。

::: flow
- 撰稿人 | 清晨起草当期通讯
- 审稿人 | 核对来源、标注问题
- 我 | 早上看汇总，确认发布 | person
- 发布渠道 | 对外发布
---
- 撰稿人 → 审稿人：交出草稿
- 审稿人 → 我：附上核对结果
- 我 → 发布渠道：批准后发布
- 发布渠道 ⇢ 我：被拦下时提醒我处理
:::

这样一来，夜里不会有没人批的卡片悄悄过期，早上需要你做的也只有一个决定。

::: prompt
你是这个团队的规划师。请为资料研究员、撰稿人、审稿人、构建师各列一份“可以直接做 / 必须先问”的清单，
并为每个“必须先问”的动作写一条一句话的“先问我”规则。只给方案，不要修改任何设置。
:::

## 社区玩法精选 {#community}

本期整理了几类常见、好上手的用法，供大家参考。都是通用思路，具体内容换成你自己的。

### 先出草稿，再谈发送 {#c1}

所有对外的消息、邮件、帖子，一律先让 Bot 出草稿给你看。草稿没有风险，看顺眼了再批准发送。

### 改动前后三件套 {#c2}

让 Bot 在任何改动前都给出“当前值、建议值、预期影响”三项。审批时一眼就能判断，也方便事后追溯。

### 定期清理“始终允许” {#c3}

“始终允许”点多了，规则表会越来越宽。每隔一段时间打开自定义规则看一遍，把不再需要或太宽的允许规则删掉。

### 只读先行 {#c4}

新接入一个工具时，先只让 Bot 做只读的任务，跑顺了再逐步放开写入。这是官方最小权限建议里的第一步。

### 看不懂就让它解释 {#c5}

遇到看不懂的审批卡片，不点任何按钮，直接问 Bot 这个动作会改什么、能不能撤销。弄明白了再决定。

## 本期小练习 {#exercise}

花 15 分钟，给你的 Bot 装上合适的“刹车”。

::: steps
- 确认开关 | 打开设置的通用页面，确认 Bot 部分的自动审查是开着的。
- 加两条“先问我” | 至少加上“对外发送任何邮件前先问我”和“付款前先问我”。
- 清理允许规则 | 看一遍已有的允许规则，删掉太宽泛的。
- 检查本地权限 | 在设置的电脑页面确认本地执行权限，不需要就选从不允许。
- 改写一个请求 | 挑一个常用的提示词，按技巧一补上“能做什么、在哪停下”。
:::
