## 本期导读 {#intro}

前面几期讲的大多是“我自己怎么用 GrokBot”。但当整个团队都要用起来时，问题就变了：谁能用、能把 Bot 分享给谁、Bot 能不能入会、能不能发邮件、哪些动作必须先问人……这些都要由团队管理员统一定下来。

本期站在管理员的角度，把官方的团队与企业版文档拆成 5 条技巧，再给一份上线清单。普通成员也值得读一遍：你在设置里看到的灰色开关和“由管理员禁用”的提示，大多来自这里。

::: callout 一句话记住本期
先确认方案、清掉网络和隐私障碍，再把共享、能力和审批的开关一项项定好；团队规则少而短，审批用自动审查来卡。
:::

## 可直接上手的 5 条技巧 {#tips}

每条技巧都附了一段示例提示词，把方括号里的内容换成你自己的，就能直接用。管理后台的设置要由管理员本人操作，提示词只是让 Bot 帮你整理和核对。

### 技巧一：先分清方案，再决定怎么开通 {#tip1}

不同方案的开通方式不一样：

| 方案 | 怎么用上 GrokBot |
| --- | --- |
| 个人 | 随付费方案提供，也可以通过 SuperGrok 个人链接或自助的 Grok Business 席位使用 |
| Teams | 默认开通，每位成员都能用，用量按席位额度计算；没有关闭它的开关 |
| Enterprise | 管理员在管理后台的 Grok Bot 页面打开，可以开放给所有成员，或用 Manage Group Access 只开放给部分分组 |

几点细节：使用旧版隐私模式或旧的按请求计费方案的 Teams 团队，GrokBot 不会开通；Enterprise 关掉总开关会挡住所有成员，但不会删除他们的电脑。两种方案的管理员都可以在 Grok Bot 页面用 Invite Team 邀请成员。很多设置只在 Enterprise 方案里出现，自助的 Teams 方案看不到。

::: prompt

3. 我需要先确认的隐私和计费前提。

### 技巧二：上线前，先清掉网络和隐私障碍 {#tip2}

官方给了一份上线前要处理的清单：

::: steps
- 离开旧版隐私模式 | Privacy Mode (Legacy) 会完全挡住 GrokBot，开通前会提示你修改，在团队设置里检查隐私选项。
- 规划出口地址 | 如果公司按来源 IP 限制服务访问，要提前规划固定的出口地址。
- 放行解密代理 | 成员设备在 Zscaler 之类的 TLS 解密代理后面时，要放行相关域名（包括多级嵌套的子域名）并免除解密检查，再让成员连接。
- 想好登录方式 | 决定成员在云端电脑上怎么登录公司工具，Okta 和 Entra ID 的配置另有专门文档。
- 核对继承的策略 | 团队规则和连接器策略对所有方案生效；团队自动审查规则和 MCP 白名单是 Enterprise 才有。
:::

::: prompt

2. 由谁负责；

:::

### 技巧三：定好分享规则：谁能分享、能不能共用账号 {#tip3}

团队 Bot 和模板怎么分享，管理员可以在 Grok Bot 页面统一定，下面几项大多在 Sharing 下：

::: props
- Bot sharing: 选 Everyone（默认）或 Admins only；选后者时成员会看到 Only team admins can share Bots，分享按钮不可用，已经分享的 Bot 保持原样
- Public template sharing: 控制成员能否把模板发布到团队之外；关闭后只能在团队内分享，已经公开的模板也会受限；Enterprise 团队默认关闭，其他团队默认允许
- Allow Shared Logins: 允许团队 Bot 的 Manager 把自己的应用账号共享给所有人用；默认关闭，打开后所有和这个 Bot 说话的人都以那个账号行事，包括它做的修改
- Slack Workspace Access: 允许 Slack 工作区里不在团队中的成员无需关联账号就在 Slack 里使用团队 Bot（限共享给整个组织的 Bot 等情况），给他们的回复计入团队用量；默认打开，Slack 访客和 Slack Connect 频道始终不包括在内
:::

另外，Grok Bot 页面的 Manage Bots 会列出团队里所有 Bot，可以按分享状态或所有者筛选，修改谁能访问；在 Auto-add 一栏选全员或某些分组，就能把这个 Bot 自动加到他们的侧边栏，这样加上的 Bot 成员不能隐藏。管理员在这里删除 Bot，会为所有人移除它和它的 Slack 应用，无法撤销。团队 Bot 本身怎么建、怎么分享，见[第 9 期](/zh/issues/2026-11-09/)。

::: prompt
我们团队准备开放团队 Bot。请帮我对比两种分享策略：
A. 所有成员都能分享，但关闭共享登录；
B. 只有管理员能分享，个别 Bot 打开共享登录。

:::

### 技巧四：逐项决定 Bot 能做什么 {#tip4}

成员的 Bot 能做哪些事，由几组开关决定：

| 开关 | 位置与默认值 | 说明 |
| --- | --- | --- |
| Meetings | Bot Capabilities 下 | 控制成员的 Bot 能否加入 Google Meet、Zoom、Microsoft Teams 会议并转写；关闭后 Bot 不能入会，也不能读取会议 |
| Agent Email | Bot Capabilities 下，默认关闭 | 打开后成员才能申领专属邮箱；Bot 自己写的邮件（包括 Routine 里的）会先存为草稿，等成员按发送 |
| Page sharing | Sharing 下，默认团队内任何人 | 可改为指定同事或关闭；收紧后已分享的页面保持分享 |
| Cloud Agents | Grok Bot 页面，默认打开 | 控制 Bot 能否把写代码的任务委派出去；团队用不上就关掉 |
| Execution on Local Computer | Grok Bot 页面，默认 Always allow | 可选 Always allow、Ask every time、Never allow；官方建议除非确有需要，选 Never allow |

应用连接不在 Grok Bot 页面单独设：它沿用团队已有的连接器策略，允许的连接器对成员的所有 Bot 都可用，被禁止的显示为 Disabled by team admin。强制推送或默认开启连接器都不支持。会议和专属邮箱的用法见[第 12 期](/zh/issues/2026-11-12/)和[第 10 期](/zh/issues/2026-11-10/)。

::: prompt
请帮我起草一份团队 GrokBot 能力开关的决定表，列出会议、专属邮箱、页面分享、委派写代码任务、在成员本机执行这几项：
1. 默认值是什么；
2. 我们 [部门或业务] 是否需要；
3. 建议开还是关，理由一句话。

:::

### 技巧五：团队规则少而短，审批交给自动审查 {#tip5}

团队规则（Team Rules）在 Grok Bot 页面添加，所有成员的 Bot 都必须遵守，成员关不掉。官方建议写得少而短，比如“绝不把公司数据转到个人账号”。规则只是指导 Bot 怎么做，真正卡住审批的是自动审查：

::: steps
- Enforce Auto-review | Enterprise 才有，默认关闭；打开后成员不能关掉自动审查，Bot 在执行风险操作前一定会检查，需要时请人审批。没人能回答审批的聊天里，团队 Bot 原本不走自动审查，打开后也一样要检查。
- Auto-review rules | Enterprise 才有，用 Configure Rules 添加团队级的“先问”和“自动允许”规则，叠加在成员自己的规则之上；冲突时“先问”优先。
- 成员这边 | 成员在 Settings → General → Auto-review 能看到团队规则，但不能修改或删除。
:::

官方建议先打开 Enforce Auto-review，再依赖团队自动审查规则。审批和自动审查的基本概念见[第 5 期](/zh/issues/2026-11-05/)。

::: prompt
请帮我把下面这些团队要求改写成不超过五条的团队规则，每条一句话，能直接给所有成员的 Bot 遵守：

:::

## 几个必须知道的边界 {#limits}

::: steps
- 很多开关只有 Enterprise 才有 | 总开关、网络控制、团队密钥、强制自动审查、团队自动审查规则等都只在 Enterprise 方案出现。
- 同一个人的 Bot 共用一台电脑 | 成员之间有硬件级隔离，但同一个成员的所有 Bot 共用一台电脑；需要独立电脑和独立凭据的工作，官方建议给它一个单独的用户。
- 终止电脑不等于收回权限 | 终止某位成员的电脑只会结束当前工作，下一条消息会在同一块持久磁盘上开一台新电脑；要收回权限，得把他移出团队或关掉他的访问。
- 共享登录要谨慎 | 打开 Allow Shared Logins 后，任何和 Bot 说话的人都能以那个账号行事，只共享不含敏感内容的账号。
- 连接器不能强推 | 只能允许或禁止，不能替成员装好或默认打开。
:::

## 实战案例：虚构的二十人设计工作室，一周内上线 GrokBot {#case}

一个虚构的场景（并非任何人的真实配置）：一家二十人左右的设计工作室，用的是 Enterprise 方案，管理员想先让项目组试用，再推给全员。

| 步骤 | 做法 | 注意点 |
| --- | --- | --- |
| 准备 | 让 Bot 按技巧二整理上线前检查表，和 IT 同事逐项确认 | 先确认没有使用旧版隐私模式 |
| 试点 | 打开总开关，用 Manage Group Access 只开放给“项目组” | 其他人暂时不受影响 |
| 定规则 | 分享改为仅管理员，关闭共享登录，本机执行选 Never allow | 团队规则只写三条 |
| 开能力 | 会议打开，专属邮箱先不开 | 试用一周再评估 |
| 推广 | 把工作室自己建的“项目排期 Bot”在 Manage Bots 里自动加给全员，再开放所有分组 | 推广前先看试点反馈 |

### 亮点：先小范围试点，再逐步放开 {#case-flow}

管理员没有一次把所有开关都打开，而是让 Bot 先帮忙整理，自己在后台逐项确认。

::: flow
- 管理员 | 说明团队情况和顾虑 | person
- 主 Bot | 整理检查表和开关建议
- IT 同事 | 确认网络和登录方式 | person
- 管理员 | 在后台逐项设置并试点 | person
---
- 管理员 → 主 Bot：我们要给项目组先开 GrokBot，帮我整理要确认的事，先别动任何设置
- 主 Bot → 管理员：整理好了：隐私设置、出口地址、代理放行、登录方式、继承的策略五类，附负责人建议
- IT 同事 → 管理员：代理已经放行并免检，可以开始试点
- 管理员 → 主 Bot：试点一周了，帮我把大家的反馈汇总成一页，标出要调整的开关
:::

一周后，管理员根据汇总把专属邮箱也打开了，并在团队规则里补上一条“对外发邮件前先问人”。

## 社区玩法精选：管理员常用的几个做法 {#community}

本期整理了几种在团队里推广 GrokBot 的做法：前两条出自官方团队 Bot 的最佳实践，后三条是基于官方设置的延伸用法，供你参考。

### 一个团队 Bot 只做一件事 {#c1}

官方建议每个团队 Bot 只负责一件事，并按这件事命名，比如发布 Bot、文案 Bot、调研 Bot。名字一看就懂，成员才知道该找谁。

### 至少两个 Manager {#c2}

团队 Bot 学到的东西要由所有者或 Manager 审核。多加一个 Manager，审核就不会卡在一个人身上。

### 规则写成一句话 {#c3}

团队规则只写真正的红线，每条一句话。细节交给各团队 Bot 自己的说明，审批交给自动审查规则。

### 先试点，再全员 {#c4}

Enterprise 可以先用 Manage Group Access 只开放给一个分组，跑顺了再放开，出问题也只影响一小部分人。

### 用 Bot 汇总成员反馈 {#c5}

试点期间，让主 Bot 每周把大家提到的问题汇总成一页，管理员只看汇总，再决定要调整哪个开关。
