## 本期导读 {#intro}

前两期我们先把一个万能助手拆成了分工明确的 Bot 小队，又给它们配上了 Routines，让它们按时自己上班。今天补上中间那块关键拼图：技能（Skills）。

你一定遇到过这种情况：花了半小时跟 Bot 来回纠正，终于让它把某件事做对了；下周再做，又得从头解释一遍。技能就是用来解决这个问题的。根据官方文档，技能是一份可复用的“这件事怎么做”的说明，会记录步骤、判断规则、期望产出和安全边界，所有 Bot 都能用。把做对的那一次存下来，以后一句话就能复现。

::: callout 一句话记住本期
技能管“怎么做”，Routine 管“什么时候做”。先把一次做对，再存成技能，写清六件事，测一遍再交给 Routine。
:::

## 可直接上手的 5 条技巧 {#tips}

每条技巧都附了一段示例提示词，把方括号里的内容换成你自己的，就能直接发给你的 Bot。

### 技巧一：在“刚做成功”的那一刻存技能 {#tip1}

官方推荐的顺序是：先把一次性任务做可靠，把做法存成技能，然后才去自动化。最适合存技能的时机，就是你刚和 Bot 一起把一件事做对、所有纠正都还留在这段对话里的时候。这时 Bot 最清楚哪些步骤是必要的、你在哪些地方改过它的做法。

值得存成技能的，通常是你会反复做、而且每次做法都差不多的事：每周的资料整理、固定格式的报告、某类邮件的处理流程。只做一次的事，就没必要存。

创建方式也很直接，在聊天里说就行：

::: prompt
这次的 [任务名] 做得很好，请把我们刚才用的流程存成一个技能，名字叫“[技能名]”。
请写进去：
1. 数据来源和需要的应用或登录；
2. 判断标准（比如什么算值得收录、什么算风险）；
3. 交付格式；
4. 我刚才纠正过你的几处地方，作为固定规则；
5. 必须先问我的事情，例如对外发送任何内容。
存好后，把技能全文发给我看一遍。
:::

### 技巧二：一份好技能写清六件事 {#tip2}

官方文档列出了一份有用的技能应该说明的六件事。存完以后，可以对照这张表检查一遍，缺哪项就让 Bot 补上：

::: props
- 什么时候用: 适用的场景，以及不适用的场景
- 输入和权限: 需要哪些数据、哪些已连接的应用或登录
- 工作顺序: 按什么步骤完成
- 怎么验证: 用什么标准检查结果是否正确
- 交付什么: 产出的内容、格式和发送位置
- 审批边界: 哪些动作必须先经过你同意
:::

除了这六件事，官方关于自动化的建议里还有两点很适合写进技能：数据缺失或数据过期时怎么办，以及只完成了一部分时向哪里汇报。没有这两条，技能在顺利的时候很好用，一遇到意外就容易拿旧数据充数。

::: proscons
#### 这样写
- 写目标和判断标准，让 Bot 自己找合适的做法
- 明确“来源打不开就如实报告失败”
- 把发送、购买、删除、发布等动作放在审批之后

#### 别这样写
- 只写一串固定的点击步骤，页面一改就失效
- 留着“尽量”“看情况”之类没有标准的说法
- 把密码、密钥直接写进技能正文
:::

::: prompt
请打开技能“[技能名]”，按这六项逐条检查：什么时候用、需要的输入和权限、工作顺序、怎么验证结果、交付什么、哪些事要先审批。
再补两条：数据缺失或过期时怎么处理；只完成一部分时怎么汇报。
把缺少或含糊的地方列出来，给出修改建议，我确认后再更新技能。
:::

### 技巧三：说不清楚的流程，就演示一遍 {#tip3}

有些事你闭着眼都会做，却很难用文字讲清楚，比如在某个后台里导出一份数据。在支持的地区，可以用演示教学（Teach a task）：

::: steps
- 打开电脑视图 | 进入和某个 Bot 的一对一对话，打开它的电脑视图。
- 开始演示 | 选择演示教学（Teach a task），先描述你接下来要演示的结果。
- 做一遍 | 亲手把流程完整操作一次。
- 审阅草稿 | 停止录制，审阅 Bot 生成的技能。
- 安全测试 | 先用安全的例子测试，再考虑交给 Routine。
:::

几点要注意：演示最长录制 10 分钟的可见电脑操作，不会录麦克风；演示过程中不要让密钥露在屏幕上，登录凭据走安全交接的流程。生成的技能只是草稿，一次演示看不出来的判断规则、失败处理和审批边界，需要你补上。

这项功能是逐步开放的。如果看不到这个按钮，就让 Bot 根据你的文字说明和已经完成的那次任务来创建技能。

::: prompt
我刚才演示了一遍 [流程名]。请把生成的技能草稿完整发给我，然后补上演示里看不出来的部分：
1. 遇到页面加载失败、找不到按钮或数据为空时怎么办；
2. 哪些操作前必须先问我；
3. 怎么确认结果是对的。
补完后，用 [一个安全的测试例子] 跑一次，把结果和每一步的依据告诉我。
:::

### 技巧四：按名字调用，善用共享技能库 {#tip4}

用技能很简单：在聊天里直接说出技能的名字，让 Bot 按它来做。所以给技能起一个一看就懂、不会和别的技能混淆的名字很重要，比如“每周资料整理”就比“整理”好用得多。

官方文档说明，私有技能是所有 Bot 共用的一个技能库：你在资料研究员那里存的技能，撰稿人也能用。不过有两个前提：

::: steps
- 应用和登录 | 某个 Bot 可能还需要连接对应的应用或登录，才能真正执行这个技能。
- 为当前 Bot 启用 | 如果 Bot 说找不到某个私有技能，在侧边栏打开连接应用（Connect apps），点标题旁边的已连接数量，在私有技能（Private skills）里为当前 Bot 启用它。
:::

另外，侧边栏的连接应用（Connect apps）里还可以发现和安装受支持的应用以及打包好的技能，不必所有东西都自己从头写。

::: prompt
请按技能“[技能名]”处理 [这次的输入]。
开始前先告诉我：这个技能需要哪些应用或登录，你这边是否都已具备；缺什么就先停下来告诉我，不要用别的方式凑合。
:::

### 技巧五：发布给团队，修改后记得同步 {#tip5}

如果你加入了团队，可以把自己的私有技能发布出去，让队友直接使用。根据官方文档，在桌面端打开连接应用（Connect apps），点标题旁边的已连接数量，打开这个技能，在顶部选择发布（Publish）；属于多个团队时，在发布到（Publish to）里选择团队。

几个细节：

::: props
- 先写描述: 技能必须有描述才能发布，因为队友和他们的 Bot 要靠描述判断什么时候该用它
- 之后的修改: 发布后按钮变成已发布（Published），它的菜单里有同步（Sync），用来把你后来的修改推送到团队的副本
- 其它操作: 同一个菜单里还有复制链接（Copy link）和取消发布（Unpublish）
- 发布失败时: 提示会说明原因，常见的是还没加入团队，或团队管理员关闭了成员发布，这时请管理员来发布
- 不能发布的: 应用自带的技能和 Bot 模板自带的技能不能发布
:::

发布之前，最好把技能里和你个人相关的内容清理一遍。描述也值得认真写，它写得越清楚，队友的 Bot 越能在合适的时候用上它。

::: prompt
我准备把技能“[技能名]”发布给团队。请先帮我做一次发布前检查：
1. 正文里有没有我的个人信息、私人账号、内部地址、密钥或只适用于我自己的设置，有就列出来并给出通用的写法；
2. 帮我写一段描述，说清楚它适合什么场景、需要哪些应用、会交付什么、哪些事要先审批；
3. 列出队友第一次使用前需要准备的东西。
先给我看修改方案，不要直接改。
:::

## 几个必须知道的边界 {#limits}

::: steps
- 技能是做法，不是权限 | 技能记录怎么做，但不会替 Bot 连上应用或登录；没有对应的访问权限，技能也跑不起来。
- 草稿要审 | 无论是演示生成的还是聊天里存的，都先读一遍、用安全的例子测一次，再交给 Routine。
- 测试会真的干活 | 测试可能会打开网站、修改文件、调用已连接的工具，所以要用安全的输入，写入类动作放在审批之后。
- 来源变了要重测 | 网站、应用或数据来源的格式变了之后，依赖它的技能要重新测试一遍。
- 密钥不进技能 | 不要把密码、密钥写进技能或露在演示里，登录凭据走安全交接。
:::

## 实战案例：一支会“传帮带”的通讯小队 {#case}

延续前两期的虚构阵容（并非任何人的真实配置）：一个小团队每周出一期通讯，同时维护一个业余小应用。这次他们把每个 Bot 做得最好的活存成技能，并让其他 Bot 也能用：

| Bot | 存下的技能 | 谁会调用 | 搭配的 Routine |
| --- | --- | --- | --- |
| 资料研究员 | 每周资料整理 | 资料研究员 | 工作日早上运行 |
| 撰稿人 | 通讯初稿格式 | 撰稿人 | 每周固定一天上午 |
| 审稿人 | 来源逐条核对 | 审稿人、撰稿人（自查） | 收到初稿时 |
| 规划师 | 周进度汇总 | 规划师 | 每周一上午 |
| 构建师 | 检查失败诊断 | 构建师 | 主分支检查失败时 |

### 亮点：一个技能，两个 Bot 共用 {#case-flow}

“来源逐条核对”最早是审稿人和你一起磨出来的：每条说法都要找到一手来源，找不到就标出来，不能删改原意。存成技能以后，撰稿人在交稿前也会先按它自查一遍，审稿人收到的初稿明显干净了。

::: flow
- 审稿人 | 和你一起把核对流程做对
- 撰稿人 | 交稿前按技能自查
- 审稿人 | 按同一技能复核
- 我 | 看结论、拍板发布 | person
---
- 审稿人 → 撰稿人：共享“来源逐条核对”技能
- 撰稿人 → 审稿人：自查后的初稿
- 审稿人 → 我：复核结论
- 审稿人 ⇢ 撰稿人：有问题打回
:::

对外发布这一步仍然留给你自己。

::: prompt
你是这个团队的规划师。请帮我梳理一下：资料研究员、撰稿人、审稿人最近反复在做哪些事，哪些值得存成技能。
请给我一张表：技能名、由谁来存、谁会调用、需要的应用或登录、是否适合再配一个 Routine。
先给方案，我确认后再分别去对应的 Bot 里创建。
:::

## 社区玩法精选 {#community}

本期整理了几类常见、好上手的技能用法，供大家参考。都是通用思路，具体内容换成你自己的。

### 固定格式的周报 {#c1}

把周报的结构、语气、数据来源和“先结论后细节”的要求存成技能。每周只需要说一句“按周报技能写本周的”，格式就不会每次都跑偏。

### 统一口径的回复草稿 {#c2}

把常见问题的回复原则、不能承诺的事项和必须转人工的情况写进技能。Bot 只负责起草，发出去之前一律由你确认。

### 演示一遍的后台导出 {#c3}

某个后台里“筛选、导出、整理成表格”的固定操作，用演示教学录一遍，比写文字说明快得多。记得先登录好，别让密码出现在录制里。

### 一致的核对清单 {#c4}

把发布前要检查的事项（链接能否打开、数字是否有来源、有没有敏感信息）存成技能，任何 Bot 交付前都按同一份清单自查。

### 技能加 Routine，定时按同一套做法跑 {#c5}

官方的示例就是这样写的：让 Routine 每个工作日早上运行某个技能，并写明数据来源不可用时报告失败、不要用旧数据。技能保证做法一致，Routine 保证按时。

## 本期小练习 {#exercise}

花 15 分钟，给你的 Bot 存下第一个技能。

::: steps
- 选一件事 | 挑一件你每周都会让 Bot 做、而且做法差不多的事，先在聊天里把它做对一次。
- 存技能 | 用技巧一的提示词，把刚才的流程存成一个名字清楚的技能。
- 查六项 | 用技巧二的提示词对照六件事检查，补上数据缺失和部分完成时的处理。
- 换个 Bot 试 | 在另一个 Bot 里按名字调用它，找不到就按技巧四为它启用。
- 测一次 | 用安全的输入跑一遍，满意了再考虑交给 Routine。
:::
